# Validation Report

## Review 1: Orchestrator & Session Manager

- [VERIFIED] `session_id` path parameter is not validated in `app.py` before being passed to `session_manager.validate_session`. An arbitrarily long or specially crafted string reaches the regex check in `session_manager.py:181` only after already being used in string formatting for log messages and URLs elsewhere in the call path; validation should be an explicit guard at the API boundary before any processing. — The regex check at `session_manager.py:181` is inside `validate_session` and only runs on the rehydration path; the ID is used in `_pool_url` (line 141) and log messages before any format validation when the session is already known.

- [VERIFIED] `validate_session` rehydrates unknown session IDs by probing the pool health endpoint (`session_manager.py:184-190`). In production (HTTPS/ACA), any attacker-supplied 16-character lowercase hex string that happens to return HTTP 200 from the pool will be permanently added to `self._sessions`, allowing the attacker to hijack or probe arbitrary ACA session containers. There is no authoritative source of truth for which session IDs this orchestrator instance actually created. — Lines 184-190 confirm: if regex passes and health probe returns 200, the ID is added to `self._sessions` with no further verification of origin.

- [VERIFIED] `_deleted_sessions` is a plain in-memory `set` that grows without bound. Every deleted session ID is appended and never pruned. Under sustained usage this is an unbounded memory leak. — Line 99 declares `self._deleted_sessions: set[str] = set()` and line 202 only adds to it; no pruning or size cap exists anywhere in the class.

- [VERIFIED] `_sessions` and `_deleted_sessions` are accessed from concurrent async tasks with no lock or other concurrency primitive. A race exists between `validate_session` checking `session_id in self._sessions` and then calling `self._sessions.add(session_id)` (lines 176-190) concurrently with `delete_session` removing the same ID (lines 201-202). The gap between the check and the add can result in a deleted session being re-added to the live set. — No `asyncio.Lock` is used anywhere in `SessionManager`; the described TOCTOU is real for concurrent async requests.

- [VERIFIED] `create_session` performs two sequential blocking HTTP calls (reset then health ping) with no timeout overrides shorter than the client default of 600 s read timeout. - [VERIFIED] `send_message` leaks the raw detail string returned by the session container directly to the frontend in `_agui_error` (line 230). - [VERIFIED] The cogservices bearer token is included in the JSON body of every `/chat/stream` POST (`chat_body["token"] = cogservices_token`, line 212). - [VERIFIED] `send_message` iterates SSE lines with `resp.aiter_lines()` but strips all empty lines (line 235-237) and then unconditionally appends `\n\n`. This means a multi-line SSE `data:` field (whose lines are separated by a single `\n`) will have the blank separator line dropped and then have `\n\n` appended, potentially corrupting the SSE framing for any event whose data spans multiple `data:` lines. — Lines 234-237: `async for line in resp.aiter_lines(): line = line.strip(); if line: yield line + "\n\n"` — all blank lines are dropped, all non-blank lines get `\n\n` appended regardless of SSE structure.

## Review 3: Frontend State & API

- [INVALID] SSE parser splits buffer on `"\n"` but the SSE spec uses `"\n\n"` (double newline) as the event delimiter. A single `"\n"` inside a multi-line `data:` value or between `event:` and `data:` fields will cause the parser to attempt a JSON parse on a partial fragment, silently discarding it. — The server (`session_manager.py:237`) always yields `line + "\n\n"` (two newlines per event), and the session container (`agent.py:179`) also formats as `data: ...\n\n`. The frontend's `split("\n")` approach works correctly for this specific server output where each non-blank chunk is a complete `data:` line followed by `\n\n`. The parser splits on `\n`, skips blank lines, and processes only lines starting with `data: `. This effectively handles the double-newline delimiter by treating each non-blank line independently. No partial fragments are produced for this server's actual output format.

- [VERIFIED] The SSE parser only recognises lines with prefix `"data: "` (with a space after the colon). The SSE spec also permits `"data:"` with no trailing space, and permits `event:`, `id:`, and `retry:` field names. Any server that omits the space or sends event/id fields will have those lines silently dropped. — `sse.ts:44`: `if (!trimmed.startsWith("data: ")) continue;` — only `"data: "` with a space is handled; all other SSE field types are dropped.

- [VERIFIED] There is no reconnection logic in `streamSSE`. If the HTTP connection drops mid-stream (network interruption, server restart) the generator simply terminates without re-connecting. The fetch is not wrapped in any retry loop; the caller in `handleSend` will fall through to a `DONE` dispatch, leaving the UI in a silently-finished state rather than an error state. — `sse.ts:33-53` and `Chat.tsx:683-694` confirm: no retry loop, a dropped connection causes the `for await` loop to exit, and `dispatch({ type: "DONE" })` is issued at line 688.

- [VERIFIED] `decoder.decode(value, { stream: true })` is correct for incremental decoding, but `decoder.decode()` is never called with no arguments (or `{ stream: false }`) after the loop ends to flush any bytes held in the decoder's internal state for multi-byte UTF-8 sequences that straddle chunk boundaries. — `sse.ts:37` calls `decoder.decode(value, { stream: true })`; no flush call exists after the `while(true)` loop exits.

- [VERIFIED] In `handleSend`, after the `for await` loop a unconditional `dispatch({ type: "DONE" })` is issued (line 688). If `RUN_FINISHED` was already received and dispatched `DONE` inside `handleAGUIEvent`, this fires a second `DONE`. — `Chat.tsx:687-688` confirms: `// Fallback: ensure streaming is closed if RUN_FINISHED was not received` then `dispatch({ type: "DONE" })` — unconditional, fires even if `RUN_FINISHED` was already handled.

Inside `handleSend`, the `for await` loop calls `handleAGUIEvent(event)` on each SSE event. If `state.sessionId` changes between when `handleSend` captured `handleAGUIEvent` and when events arrive, the stale closure's `state.sessionId` is used for the `refreshFiles` call. — `Chat.tsx:671` confirms `useCallback([refreshFiles, state.sessionId])`; stale-closure risk on `state.sessionId` inside the async `handleSend` is real.

- [VERIFIED] `handleSend` is memoised with deps `[handleAGUIEvent, state.sessionId, state.isStreaming]`. Between when `handleSend` starts the `for await` loop and when it finishes, `state.isStreaming` and `state.sessionId` inside the async closure are the values captured at call time — React state updates are not reflected inside the already-running async function. A mid-stream `RESET_FOR_NEW_CHAT` will clear `state.sessionId` in the reducer but the running `for await` loop continues dispatching events against the old session. — `Chat.tsx:673-697` confirms; `abortRef.current?.abort()` in `handleNewChat` is the only interruption mechanism, but events can still be dispatched before the abort propagates.
