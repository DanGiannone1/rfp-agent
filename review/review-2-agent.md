# Review 2: Session Container Agent

## Observations

- [OBSERVATION] `_get_or_create_session` reads and writes `_session` without holding `_lock`, creating a TOCTOU race: two concurrent requests can both observe `_session is None` simultaneously and construct two `AgentSession` objects, with the second overwriting the first and leaking the first session's resources. | severity: high | session-container/server.py:42-49

- [OBSERVATION] The `generate()` coroutine in `chat_stream` acquires `_lock` for the entire duration of the agent turn (lines 83-87), meaning all other HTTP requests — including `/upload`, `/files`, and `/reset` — are not blocked by the same lock, but any second concurrent `/chat/stream` call will hang indefinitely until the first completes, with no timeout applied to the lock acquisition itself. A malicious or slow agent turn can thus deny all subsequent chat requests without error. | severity: medium | session-container/server.py:83-87

- [OBSERVATION] On `TimeoutError`, the code attempts to acquire `_lock` again (line 90) while already inside the `async with _lock:` block (line 83). `asyncio.Lock` is not re-entrant; this will deadlock permanently, hanging the response and making the server unresponsive until the process is killed. | severity: high | session-container/server.py:88-93

- [OBSERVATION] The same re-entrant deadlock applies to the `except Exception` branch (line 96-98): `_lock` is already held by the outer `async with _lock:` on line 83, and re-acquiring it on line 96 will deadlock. | severity: high | session-container/server.py:94-99

- [OBSERVATION] `thread_id` and `run_id` for the error/timeout `RunFinishedEvent` (lines 93, 99) are generated fresh inside `generate()` and are unrelated to the `run_id` already emitted in `RunStartedEvent` (which is generated inside `session.send()`). The client will receive a `RunFinishedEvent` with a mismatched `run_id`, breaking AG-UI protocol state tracking. | severity: medium | session-container/server.py:80-81, 93, 99

- [OBSERVATION] `asyncio.Queue` is constructed with no `maxsize` argument (line 198), so it is unbounded. A fast SDK that emits many events — or a stuck consumer — will accumulate an unlimited number of events in memory, with no backpressure applied to the SDK callback thread. | severity: medium | session-container/agent.py:198

- [OBSERVATION] `_enqueue` calls `self._loop.call_soon_threadsafe(self._queue.put_nowait, event)` (line 305). If the queue were bounded, `put_nowait` would raise `QueueFull` silently on the event loop thread with no error propagation — events would be silently dropped with no notification to the caller. | severity: low | session-container/agent.py:305

- [OBSERVATION] `_on_event` is described as running "from the SDK's internal thread" (line 308), but it mutates multiple instance fields — `self._status`, `self._message_started`, `self._current_message_id`, `self._tool_names`, `self._run_id`, `self._thread_id` — without any locking. If the SDK does run callbacks on a different thread, all of these reads and writes are unsynchronised and subject to data races. | severity: high | session-container/agent.py:307-404

- [OBSERVATION] `self._tool_names` is a plain `dict` that is written in `_on_event` (potentially from a background thread) and read/popped in the same callback without any lock. Concurrent tool-start and tool-complete events for different tools could corrupt the dict or produce incorrect `call_id` lookups. | severity: medium | session-container/agent.py:341, 371

- [OBSERVATION] In `send()`, stale queue items from a previous turn are drained with a synchronous loop calling `get_nowait()` (lines 409-410). If `_on_event` is firing concurrently on another thread and enqueuing items while the drain is running, new items can arrive immediately after the drain, causing events from the previous turn to be interpreted as belonging to the new turn. | severity: medium | session-container/agent.py:409-410

- [OBSERVATION] The `SESSION_IDLE` handler enqueues `RunFinishedEvent` and then separately enqueues the sentinel `None` via another `call_soon_threadsafe` call (lines 385-386). Because both are scheduled as separate callbacks, another event from the SDK could be enqueued between the `RunFinishedEvent` and the `None` sentinel, causing the consumer in `send()` to yield one or more extra post-completion events before seeing `None`. | severity: low | session-container/agent.py:382-387

- [OBSERVATION] The `SESSION_ERROR` handler (lines 389-404) enqueues a `RunErrorEvent` but does not enqueue a `RunFinishedEvent` before the `None` sentinel. The consumer in `send()` will therefore terminate after `RunErrorEvent` without ever emitting `RunFinishedEvent`, breaking AG-UI protocol expectations for clients that rely on `RunFinishedEvent` to close the run lifecycle. | severity: medium | session-container/agent.py:389-404

- [OBSERVATION] `_on_event` has no handling for unrecognised `SessionEventType` values. If the SDK emits a new or unexpected event type, it is silently ignored. While not always a problem, it means future SDK upgrades could silently stop delivering events the agent should be tracking (e.g. a new streaming-complete event type). | severity: low | session-container/agent.py:307-404

- [OBSERVATION] The `TOOL_EXECUTION_COMPLETE` fallback ID recovery (lines 364-369) iterates `self._tool_names.items()` and returns the first key whose value matches `tool_name_hint`. If the same tool is called multiple times concurrently and the first call's entry was already popped, a subsequent completion will match the still-in-dict entry from a different invocation, emitting `ToolCallEndEvent` with the wrong `tool_call_id` and leaking the matched entry in `self._tool_names`. | severity: medium | session-container/agent.py:364-371

- [OBSERVATION] The system prompt grants the agent "full shell access" and instructs it to write and execute Python scripts (lines 48-58), while the `CopilotClient` is initialised with `--allow-all-tools` and `--allow-all-paths` (line 225). The system prompt is not treated as untrusted; any user-supplied RFP document content that is read into the agent context could inject instructions that override the persona, exfiltrate workspace data via bash, or escape the intended tool scope. There is no sandboxing of what shell commands the agent will actually execute. | severity: high | session-container/agent.py:48-58, 225

- [OBSERVATION] `SEARCH_KEY` (the Azure AI Search API key) is injected directly into the MCP server HTTP headers at session creation time (line 282). The key is a static secret read from the environment and sent verbatim on every MCP request. If the Copilot SDK logs request headers or the key leaks via a tool result, it would be fully exposed. There is no use of managed identity or short-lived tokens for the search service. | severity: medium | session-container/agent.py:282-283

- [OBSERVATION] The `bearer_token` for Azure OpenAI is passed inside the `session_config` dict (line 259). If the Copilot SDK serialises this config to disk or logs it (e.g. for debugging), the token would be written in plaintext. There is no indication the SDK treats this field as sensitive. | severity: medium | session-container/agent.py:252-262

- [OBSERVATION] `DefaultAzureCredential.get_token()` is called once during `__aenter__` (lines 219-221) and the resulting token is stored for the lifetime of the session. Azure tokens typically expire after 1 hour. Long-lived sessions (e.g. an RFP analysis spanning multiple turns over hours) will use an expired token without any refresh logic. | severity: medium | session-container/agent.py:216-221

- [OBSERVATION] The `on_permission_request` lambda unconditionally returns `{"kind": "approved"}` for all permission requests (line 268), meaning the agent is auto-approved to use any tool with any arguments, including arbitrary shell commands, file reads, and network access. There is no allowlist of approved tool/argument combinations. | severity: high | session-container/agent.py:268

- [OBSERVATION] The upload endpoint uses `PurePosixPath(raw_name).name` to strip path components (line 118). On a host running Windows, `PurePosixPath` would not strip Windows-style path separators (backslashes), allowing a filename like `..\\etc\\passwd` to pass the strip and reach `os.path.join(WORKSPACE, safe_name)`. The subsequent `os.path.realpath` check would catch it, but the POSIX-only path stripping is a brittle first defence on non-POSIX systems. | severity: low | session-container/server.py:118

- [OBSERVATION] The upload endpoint checks the size limit by accumulating `bytes_written` and comparing after each 8192-byte chunk (lines 140-148). The check is `bytes_written > UPLOAD_MAX_BYTES` rather than `>=`, so a file of exactly 50 MB + 1 byte triggers deletion, but a file of exactly 52,428,800 bytes (50 * 1024 * 1024) would be written fully without triggering the limit. This is an off-by-one that allows files of exactly the limit size to pass. | severity: low | session-container/server.py:144

- [OBSERVATION] On upload size limit exceeded, `f.close()` is called explicitly (line 145) while the `with open(...)` context manager is still active (line 141). When the `with` block exits after the `HTTPException` is raised, it will call `__exit__` on an already-closed file object, which CPython tolerates but is undefined behaviour in the file protocol and could fail on alternative Python implementations. | severity: low | session-container/server.py:145-147

- [OBSERVATION] `_read_uploaded_manifest` and `_write_uploaded_manifest` are synchronous blocking I/O functions called from async endpoint handlers (lines 152-158, 172). They are not run in a thread executor, so they block the event loop while reading/writing the manifest JSON file. Under load, this can delay all other async request handling. | severity: low | session-container/server.py:152-158, 172

- [OBSERVATION] `_read_uploaded_manifest` is called in `list_files()` (line 172) without acquiring `_manifest_lock`, while writes to the manifest in `upload()` are protected by `_manifest_lock` (line 151). A concurrent upload and file listing can therefore read a partially written or inconsistent manifest, causing a newly uploaded file to appear with `origin: "generated"` instead of `"uploaded"`. | severity: low | session-container/server.py:172

- [OBSERVATION] The `/reset` endpoint is unauthenticated and has no access control (line 229). Any caller who can reach the session container network — including other tenants in a misconfigured ACA environment or a SSRF from within the agent's bash tool — can destroy the agent session and wipe the entire workspace without warning. | severity: high | session-container/server.py:229-253

- [OBSERVATION] `AgentSession.__aexit__` does not drain or close `self._queue` before returning (lines 293-301). If `_on_event` fires during or just after teardown (e.g. the SDK emits a final event while `destroy()` is running), `_enqueue` will call `self._loop.call_soon_threadsafe` on a queue that no consumer is watching, silently dropping the event and potentially leaving a reference alive after the session object is intended to be discarded. | severity: low | session-container/agent.py:293-301

- [OBSERVATION] `run_analysis` in agent.py (lines 432-442) catches all exceptions and emits a `RunErrorEvent` with `str(exc)` as the message. This can expose internal exception details — including file paths, environment variable names, or SDK internals — directly to the SSE consumer/client. | severity: low | session-container/agent.py:442
