# Review 4: Frontend Components

## Observations

- [OBSERVATION] `toolLabelForStatus` in MessageBubble.tsx duplicates the `toolLabel` function in both AgentActivityBar.tsx and ToolIndicator.tsx but with a different label set (e.g., AgentActivityBar has no `read_file`/`write_file`/`search` labels, MessageBubble has both running and done variants). This divergence means the same tool name renders a different human-readable string depending on which component displays it, creating inconsistent UX. | severity: medium | MessageBubble.tsx:60-79, AgentActivityBar.tsx:11-22, ToolIndicator.tsx:7-26

- [OBSERVATION] `toolContext` is copy-pasted in all three files with only minor differences (MessageBubble omits the surrounding quotes on `grep` and `knowledge_base_retrieve`, the other two include them). Any future tool requiring context extraction must be updated in three places, and the current inconsistency already produces differing output for the same tool call. | severity: medium | MessageBubble.tsx:81-96, AgentActivityBar.tsx:24-37, ToolIndicator.tsx:28-49

- [OBSERVATION] In `MessageBubble.tsx`, the `CodeBlock` component extracts `codeChild` from `children` using index 0 or a direct cast but performs no runtime check that `codeChild` is actually a React element with `props`. If `children` is a string, null, or a non-element node (possible when rehype-highlight wraps content differently), `codeChild?.props?.children` silently returns `undefined` and the copy button becomes a no-op with no user feedback. | severity: medium | MessageBubble.tsx:17-32

- [OBSERVATION] In `handleCopy` (MessageBubble.tsx line 26-31), `navigator.clipboard.writeText` returns a Promise that is not awaited and its rejection is not caught. On HTTP origins or in browsers that deny clipboard access, the copy silently fails while the button still shows "Copied" for 1.8 seconds, misleading the user. | severity: medium | MessageBubble.tsx:28-30

- [OBSERVATION] In `MessageBubble.tsx`, `message.content` is passed directly to `<ReactMarkdown>` for user messages (line 217) without any sanitisation. `rehype-highlight` is applied but no `rehype-sanitize` plugin is included. If `message.content` ever contains HTML (e.g., from a pasted user input that the SSE stream reflects back verbatim), ReactMarkdown with no sanitizer can pass raw HTML through to the DOM via `rehype-raw` or future plugin additions. While currently safe because `rehype-raw` is not listed, the absence of an explicit sanitize step is a latent XSS risk. | severity: medium | MessageBubble.tsx:216-219

- [OBSERVATION] Segments in the assistant message path use `seg.index` (the original part index in `message.parts`) as the React `key` for text segments (line 227). If `message.parts` is mutated by prepending or inserting parts mid-stream, the index-based key will cause React to reuse the wrong DOM nodes. A stable key derived from part identity (e.g., a part id or content hash) would be safer. | severity: low | MessageBubble.tsx:227

- [OBSERVATION] `ToolGroup` uses `part.toolCallId` as the React key (line 179). The `MessagePart` type defines `toolCallId` on the `tool_call` variant. If `toolCallId` is ever an empty string (the type does not enforce non-empty), multiple parts would share the same key, causing React key collisions. No guard is present. | severity: low | MessageBubble.tsx:179

- [OBSERVATION] `ToolGroup` has a `canCollapse` condition requiring `parts.length > 2` (line 152), meaning groups of exactly 2 tool calls are never collapsible. The threshold is undocumented and may be unintentional — a group of 2 done steps still occupies space the user cannot collapse. | severity: low | MessageBubble.tsx:152

- [OBSERVATION] The `ToolGroup` toggle button (line 159-177) has `aria-expanded` set but no `aria-controls` attribute pointing to the collapsible region it toggles. Screen readers cannot programmatically associate the button with the content it controls. | severity: medium | MessageBubble.tsx:159-177

- [OBSERVATION] The `ToolGroup` toggle button SVG chevron (line 165-167) has no `aria-hidden="true"` attribute. It will be announced by screen readers as an unlabelled graphic inside an already-labelled button, producing redundant or confusing output. | severity: low | MessageBubble.tsx:165-167

- [OBSERVATION] The `InlineToolCall` component renders tool context in a `<span title={ctx}>` (line 116) which truncates via CSS but exposes the full value only on hover (title tooltip). Keyboard-only users cannot trigger a title tooltip; if the context string is important (e.g., a file path), it is inaccessible without a mouse. | severity: low | MessageBubble.tsx:116

- [OBSERVATION] The assistant message avatar SVG (line 198-200) has `aria-hidden="true"` correctly, but the `<article>` element wrapping each message has no `aria-label` or `aria-roledescription`. Screen readers will announce it as "article" with no additional context, giving no indication whether it is a user or assistant message. | severity: medium | MessageBubble.tsx:195

- [OBSERVATION] `isThinking` is `true` only when `isStreaming && !hasContent && !hasTools` (line 190). If a message arrives with `isStreaming: false` but `parts` is empty (e.g., a race condition where the SSE `done` event fires before any content parts), both `isThinking` and `hasParts` are false, resulting in a completely empty `<article>` being rendered with no visible content and no accessible announcement. | severity: low | MessageBubble.tsx:187-190

- [OBSERVATION] The "thinking" indicator uses a `<div role="status">` with `aria-label="Agent is thinking"` (line 206), which is correct live-region usage. However, the identical pattern is repeated at line 247 for the post-tool-call thinking state. The duplicate `role="status"` elements can both be present in the DOM simultaneously during streaming, which may cause double announcements on some screen readers. | severity: low | MessageBubble.tsx:206, 247

- [OBSERVATION] In `AgentActivityBar.tsx`, the `isExpanded` value on line 54 uses a ternary that ignores the `expanded` state entirely when `running.length > 0 || isStreaming`. This means once the user collapses the panel and then a new tool starts running, the panel snaps back open without user intent. This is a deliberate design choice but there is no visual affordance (e.g., a transition or animation) to inform the user the panel re-expanded automatically. | severity: low | AgentActivityBar.tsx:54

- [OBSERVATION] `AgentActivityBar` shows only `visibleItems = toolActivity.slice(-4)` (line 52), silently discarding earlier activities. There is no indicator shown to the user that older steps were hidden (e.g., no "and N more" message), so completed work disappears without explanation. | severity: low | AgentActivityBar.tsx:52-53

- [OBSERVATION] In `AgentActivityBar.tsx`, `canToggle` is `visibleItems.length > 0` (line 53) but `visibleItems` is always a subset of `toolActivity`, which is already checked by `hasActivity` at line 42. When `isStreaming` is true but `toolActivity` is empty, `hasActivity` is true (component renders) but `canToggle` is false and `visibleItems` is empty — the section renders with only the status pill and no toggle, which is fine, but the expand/collapse state variable remains in memory and its stale value could be applied unexpectedly when items later appear. | severity: low | AgentActivityBar.tsx:42-53

- [OBSERVATION] The spinning SVG in `AgentActivityBar.tsx` (line 91) has no `aria-label` or `aria-hidden` attribute. Screen readers will attempt to interpret it as meaningful content and may announce it as an unlabelled image. | severity: medium | AgentActivityBar.tsx:91-93

- [OBSERVATION] The completed-checkmark SVG in `AgentActivityBar.tsx` (line 95) likewise has no `aria-hidden="true"`. The done-state icon will be announced by screen readers as an unlabelled graphic. | severity: low | AgentActivityBar.tsx:95-97

- [OBSERVATION] `AgentActivityBar` is a `<section>` element (line 59) with no `aria-label`. A `<section>` without an accessible name is not treated as a landmark by assistive technologies in most browsers, making it indistinguishable from a plain `<div>`. Either add `aria-label="Agent activity"` or change the element to a `<div>`. | severity: low | AgentActivityBar.tsx:59

- [OBSERVATION] In `ToolIndicator.tsx`, the component is exported as a default export but appears not to be used anywhere — `AgentActivityBar` renders tool items inline and `MessageBubble` uses `InlineToolCall`. If `ToolIndicator` has been superseded, it is dead code that still carries maintenance burden (including the duplicated `toolLabel`/`toolContext` logic). | severity: low | ToolIndicator.tsx:51

- [OBSERVATION] In `ToolIndicator.tsx`, the running-state spinner SVG (line 59-61) and the done-state checkmark SVG (line 63-65) both have no `aria-hidden="true"` and no `aria-label`. Screen readers will encounter unlabelled graphics. The text label at line 67 conveys the same information, so these icons should be hidden from the accessibility tree. | severity: medium | ToolIndicator.tsx:59-65

- [OBSERVATION] In `ToolIndicator.tsx`, the status text "…" for running and "Done" for done (line 71) redundantly re-states what the adjacent label (line 67) and icon already convey. For a screen reader this results in e.g. "Running command … Done" being announced, which is confusing. | severity: low | ToolIndicator.tsx:71

- [OBSERVATION] `ToolIndicator.tsx` uses a custom CSS class `tool-item` and `tool-item-running`/`tool-item-done` (line 56) rather than inline Tailwind, while `AgentActivityBar` uses inline Tailwind exclusively. This creates an inconsistent styling approach across the two components that serve the same visual purpose. | severity: low | ToolIndicator.tsx:56, AgentActivityBar.tsx:89

- [OBSERVATION] In `MessageBubble.tsx`, `markdownComponents` is defined at module scope as a plain object (line 55-58). This is correct and avoids per-render allocation. However, `CodeBlock` and `TableWrapper` are also defined at module scope, so re-renders of `MessageBubble` do not re-create these — no issue here, but worth noting that `remarkPlugins` and `rehypePlugins` arrays are constructed as inline literals on lines 216 and 228, creating new array references on every render and potentially causing ReactMarkdown to re-run its plugin pipeline unnecessarily. | severity: low | MessageBubble.tsx:216, 228

- [OBSERVATION] In `MessageBubble.tsx`, `groupParts` is memoised via `useMemo` with `message.parts` as a dependency (line 192). Since `message.parts` is an array, the memo only re-runs if the array reference changes. If the parent mutates the array in place rather than replacing it, the memo will return a stale result. The types do not enforce immutability. | severity: low | MessageBubble.tsx:192

- [OBSERVATION] In `MessageBubble.tsx`, the `isLast` check on line 225 compares `seg.index` (the original part index) against `message.parts.length - 1`. Because `seg.index` is set to the loop variable `i` at insertion time in `groupParts` and tool_call parts consume indices without creating text segments, a text segment that is not actually the final element in `parts` could still be treated as last if there are trailing tool_call parts — the streaming cursor would appear mid-message. | severity: medium | MessageBubble.tsx:225, 231

- [OBSERVATION] The `toolContext` function in `MessageBubble.tsx` does not handle the `view` or `read_file` tool names in the switch, even though `toolLabelForStatus` includes labels for both (lines 65, 91). This means files being read/viewed will never show a path as context, while the label says "Reading file". The other two files (AgentActivityBar, ToolIndicator) also omit `view` from their `toolContext` switch, but their label maps also omit it or are consistent. | severity: low | MessageBubble.tsx:85-95

- [OBSERVATION] `AgentActivityBar`'s `toolContext` for `glob` returns `p.pattern || null` (line 30) without the `String()` cast applied to `grep` and `knowledge_base_retrieve`. If `p.pattern` is a non-string truthy value (e.g., a number or object), it will be coerced to string by JSX interpolation at render time, but the inconsistency could silently propagate unexpected types. The same inconsistency exists in `ToolIndicator.tsx` line 36. | severity: low | AgentActivityBar.tsx:30, ToolIndicator.tsx:36

- [OBSERVATION] In `MessageBubble.tsx`, `toolContext` for `glob` returns `p.pattern || null` (line 87) without a `String()` cast, and for `str_replace_editor` and `view` returns `p.path || null` (lines 90-91) also without casting, inconsistent with the explicit `String()` wraps applied to `grep` and `knowledge_base_retrieve` patterns in the same switch. | severity: low | MessageBubble.tsx:87-91
