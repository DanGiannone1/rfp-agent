# Review 1: Orchestrator & Session Manager

## Observations

- [OBSERVATION] `session_id` path parameter is not validated in `app.py` before being passed to `session_manager.validate_session`. An arbitrarily long or specially crafted string reaches the regex check in `session_manager.py:181` only after already being used in string formatting for log messages and URLs elsewhere in the call path; validation should be an explicit guard at the API boundary before any processing. | severity: medium | app.py:94

- [OBSERVATION] `validate_session` rehydrates unknown session IDs by probing the pool health endpoint (`session_manager.py:184-190`). In production (HTTPS/ACA), any attacker-supplied 16-character lowercase hex string that happens to return HTTP 200 from the pool will be permanently added to `self._sessions`, allowing the attacker to hijack or probe arbitrary ACA session containers. There is no authoritative source of truth for which session IDs this orchestrator instance actually created. | severity: high | session_manager.py:184-190

- [OBSERVATION] `_deleted_sessions` is a plain in-memory `set` that grows without bound. Every deleted session ID is appended and never pruned. Under sustained usage this is an unbounded memory leak. | severity: medium | session_manager.py:99

- [OBSERVATION] `_sessions` and `_deleted_sessions` are accessed from concurrent async tasks with no lock or other concurrency primitive. A race exists between `validate_session` checking `session_id in self._sessions` and then calling `self._sessions.add(session_id)` (lines 176-190) concurrently with `delete_session` removing the same ID (lines 201-202). The gap between the check and the add can result in a deleted session being re-added to the live set. | severity: medium | session_manager.py:176-202

- [OBSERVATION] `create_session` performs two sequential blocking HTTP calls (reset then health ping) with no timeout overrides shorter than the client default of 600 s read timeout. A hung container can stall session creation for up to 10 minutes, blocking the event loop task for that duration and degrading all other in-flight requests. | severity: medium | session_manager.py:151-159

- [OBSERVATION] `send_message` leaks the raw detail string returned by the session container directly to the frontend in `_agui_error` (line 230). If the container ever includes internal paths, stack traces, or infrastructure hostnames in its error responses, those are forwarded verbatim to the client. | severity: medium | session_manager.py:230

- [OBSERVATION] The cogservices bearer token is included in the JSON body of every `/chat/stream` POST (`chat_body["token"] = cogservices_token`, line 212). This means the live Azure Cognitive Services token is transmitted as plain JSON, visible in any proxy/log that records request bodies, and is accessible to the session container process in its request handler rather than being confined to a header. | severity: high | session_manager.py:211-212

- [OBSERVATION] `send_message` iterates SSE lines with `resp.aiter_lines()` but strips all empty lines (line 235-237) and then unconditionally appends `\n\n`. This means a multi-line SSE `data:` field (whose lines are separated by a single `\n`) will have the blank separator line dropped and then have `\n\n` appended, potentially corrupting the SSE framing for any event whose data spans multiple `data:` lines. | severity: medium | session_manager.py:234-237

- [OBSERVATION] `send_message` does not yield a `_agui_finished()` event when the upstream SSE stream ends normally (i.e., after the `async for` loop completes without error). The `RUN_FINISHED` sentinel is only emitted on error paths (lines 217, 232, 242). If the session container itself sends a proper done/finished event the frontend may be fine, but if it does not the frontend will hang waiting for a terminal event that never arrives. | severity: medium | session_manager.py:234-242

- [OBSERVATION] `upload_file` reads the file body into memory with `await upload_file.read(max_bytes + 1)` (line 248) and then holds the full bytes in `content` for the entire duration of the subsequent `process_document` call (which involves an ADLS upload and a Content Understanding HTTP round-trip). This means up to ~50 MB per request is pinned in process memory for potentially minutes, making the server vulnerable to memory exhaustion under concurrent uploads. | severity: medium | session_manager.py:248

- [OBSERVATION] `upload_file` passes `upload_file.filename` without any sanitisation to the multipart POST to the session container (line 254). A client can supply a filename containing path traversal sequences (e.g. `../../etc/passwd`) or special characters. Sanitisation happens, if at all, only inside the session container — the orchestrator performs no validation. | severity: high | session_manager.py:252-254

- [OBSERVATION] `get_file_content` passes the `filename` query parameter received from the frontend directly to the session container's `/files/content` endpoint with no validation or sanitisation (line 302). The same path-traversal risk as the upload filename applies: an attacker can supply arbitrary values to probe the container's filesystem via the `filename` query parameter. | severity: high | app.py:146 / session_manager.py:302

- [OBSERVATION] `_pool_url` constructs the URL by simple string concatenation of `POOL_MANAGEMENT_ENDPOINT` and `path`, with `session_id` appended as the `identifier` query parameter (line 141). If `POOL_MANAGEMENT_ENDPOINT` is not set (empty string, the default), all URLs become relative paths like `/health?identifier=...` which will cause confusing failures rather than a clear startup error. There is no validation that the env var is present and well-formed at startup. | severity: medium | session_manager.py:139-141

- [OBSERVATION] `_pool_url` appends `session_id` directly into the query string without URL-encoding (line 141). Although the regex at line 24 constrains locally-created IDs to `[0-9a-f]{16}`, the rehydration path in `validate_session` calls `_pool_url` before the regex check executes (lines 184 vs 181), so a crafted ID could in theory inject additional query parameters via `&` or `=` characters in the brief window where order matters. | severity: low | session_manager.py:139-141

- [OBSERVATION] The `send_message` endpoint in `app.py` (line 91) accepts a `prompt` field with no length or content validation. An arbitrarily large prompt string is passed directly to the session container. This can be used to inflate request body sizes and stress downstream infrastructure with no server-side guard. | severity: medium | app.py:76-99

- [OBSERVATION] `app.py` exposes a `GET /health` endpoint with no authentication (line 193-196). While this is common practice, combined with the unauthenticated session CRUD endpoints (`POST /sessions`, `GET /sessions/{id}`, `DELETE /sessions/{id}`) there is no authentication layer at all on the orchestrator. Any client on the network can create, probe, or delete sessions without credentials. | severity: high | app.py:83-125

- [OBSERVATION] `delete_session` catches all exceptions from the reset call silently at DEBUG level and always continues to remove the session from the live set (lines 195-202). If the reset fails (e.g., network error), the session container retains its state (workspace files, agent history) while the orchestrator believes the session is gone. A subsequent new session for the same logical user on the same local container will see stale data, and there is no retry or alert mechanism. | severity: medium | session_manager.py:195-202

- [OBSERVATION] In `app.py:138-142`, a bare `raise` re-raises the original exception for HTTP 5xx errors from the session container, which will produce an unhandled-exception 500 response from FastAPI and may include a Python traceback in the response body depending on the FastAPI debug configuration. No explicit `HTTPException` wrapping is applied for the 5xx case, and the same pattern is repeated for `get_file_content` (lines 155-164) and `upload_file` (lines 179-186). | severity: medium | app.py:138-142, 155-164, 179-186

- [OBSERVATION] `_SessionPoolAuth` caches the token in instance state (`self._token`, `self._expires_on`) and refreshes it in `_refresh` with no async lock. Under concurrent requests two coroutines can both observe an expired token simultaneously, both call `get_token`, and both overwrite the cached value. While not catastrophic (both will get valid tokens), it results in redundant token acquisitions and could exhaust token-request rate limits under high concurrency. | severity: low | session_manager.py:60-73

- [OBSERVATION] The same double-refresh race applies to `_get_cogservices_token` (lines 114-123), which shares the same check-then-set pattern without an async lock. | severity: low | session_manager.py:114-123
