# Review 3: Frontend State & API

## Observations

- [OBSERVATION] SSE parser splits buffer on `"\n"` but the SSE spec uses `"\n\n"` (double newline) as the event delimiter. A single `"\n"` inside a multi-line `data:` value or between `event:` and `data:` fields will cause the parser to attempt a JSON parse on a partial fragment, silently discarding it. | severity: high | frontend/src/lib/sse.ts:39-52

- [OBSERVATION] The SSE parser only recognises lines with prefix `"data: "` (with a space after the colon). The SSE spec also permits `"data:"` with no trailing space, and permits `event:`, `id:`, and `retry:` field names. Any server that omits the space or sends event/id fields will have those lines silently dropped. | severity: medium | frontend/src/lib/sse.ts:44-45

- [OBSERVATION] There is no reconnection logic in `streamSSE`. If the HTTP connection drops mid-stream (network interruption, server restart) the generator simply terminates without re-connecting. The fetch is not wrapped in any retry loop; the caller in `handleSend` will fall through to a `DONE` dispatch, leaving the UI in a silently-finished state rather than an error state. | severity: high | frontend/src/lib/sse.ts:33-53

- [OBSERVATION] `decoder.decode(value, { stream: true })` is correct for incremental decoding, but `decoder.decode()` is never called with no arguments (or `{ stream: false }`) after the loop ends to flush any bytes held in the decoder's internal state for multi-byte UTF-8 sequences that straddle chunk boundaries. The remaining-buffer check at lines 56-64 will see the un-flushed bytes only as whatever was left in `buffer`, not the decoder's internal pending bytes. | severity: low | frontend/src/lib/sse.ts:37

- [OBSERVATION] `buffer = lines.pop()!` uses a non-null assertion. `String.prototype.split` on a non-empty string always returns at least one element so `pop()` cannot actually return `undefined` here, but if `buffer` were already empty and `value` decoded to an empty string, `lines` would be `[""]` and `pop()` would return `""` — harmless but the `!` masks the assumption. | severity: low | frontend/src/lib/sse.ts:40

- [OBSERVATION] In `handleSend`, after the `for await` loop a unconditional `dispatch({ type: "DONE" })` is issued (line 688). If `RUN_FINISHED` was already received and dispatched `DONE` inside `handleAGUIEvent`, this fires a second `DONE`, which calls `updateLastMessage` again and re-runs `syncFromParts` on the final message. This is mostly idempotent but sets `isStreaming: false` and `currentRunId: null` twice, and maps tool-call parts to `"done"` a second time unnecessarily. | severity: low | frontend/src/components/Chat.tsx:688

- [OBSERVATION] `handleAGUIEvent` closes over `state.sessionId` and `refreshFiles` via `useCallback` with `[refreshFiles, state.sessionId]` as deps. Inside `handleSend`, the `for await` loop calls `handleAGUIEvent(event)` on each SSE event. If `state.sessionId` changes between when `handleSend` captured `handleAGUIEvent` and when events arrive (e.g. during a new-chat race), the stale closure's `state.sessionId` is used for the `refreshFiles` call inside `RUN_FINISHED`/`RUN_ERROR` handling. | severity: medium | frontend/src/components/Chat.tsx:671

- [OBSERVATION] `handleSend` is memoised with deps `[handleAGUIEvent, state.sessionId, state.isStreaming]`. Because `handleAGUIEvent` itself depends on `state.sessionId`, any `sessionId` change rebuilds both callbacks. However, between when `handleSend` starts the `for await` loop and when it finishes, `state.isStreaming` and `state.sessionId` inside the async closure are the values captured at call time — React state updates are not reflected inside the already-running async function. A mid-stream `RESET_FOR_NEW_CHAT` (from `handleNewChat`) will clear `state.sessionId` in the reducer but the running `for await` loop continues dispatching events (including `DONE`, `FILES_CHANGED`, `refreshFiles`) against the old session. The `abortRef.current?.abort()` call in `handleNewChat` does abort the fetch, but the abort only takes effect at the next `await reader.read()` inside `streamSSE`, so several events may still be dispatched after `RESET_FOR_NEW_CHAT`. | severity: high | frontend/src/components/Chat.tsx:673-697

- [OBSERVATION] In `handleNewChat`, `abortRef.current?.abort()` is called and then immediately `abortRef.current = null` (line 593-594), then `dispatch({ type: "RESET_FOR_NEW_CHAT" })` is called (line 614), and then `await startSession()` (line 616). If `handleSend`'s `catch` block runs after the abort (because the abort rejection arrives asynchronously), it checks `err.name === "AbortError"` and returns early — so no double error dispatch. However, the `finally` block in `handleSend` sets `abortRef.current = null` again, which is safe since `handleNewChat` already nulled it, but reveals a race: if `startSession` creates a new session and a new `AbortController` is assigned to `abortRef.current` before `handleSend`'s `finally` runs, `handleSend`'s `finally` will null out the newly-created controller for the next request. | severity: medium | frontend/src/components/Chat.tsx:619-625 and 693

- [OBSERVATION] `handleAGUIEvent` is called inside the `for await` loop in `handleSend` synchronously per event, but `handleAGUIEvent` itself calls `void refreshFiles(sid).catch(() => {})` and schedules a `setTimeout` for a second `refreshFiles` call (lines 655-657). Neither of these calls is tracked by the `abortRef`. If the component unmounts or `handleNewChat` is called while these fire-and-forget promises are in-flight, `setServerFiles` and `setPendingFiles` will be called on an unmounted component (or on a fresh session's state), causing potential state corruption or React warnings. | severity: medium | frontend/src/components/Chat.tsx:653-658

- [OBSERVATION] The file-polling `useEffect` (lines 524-545) triggers on `state.fileRefreshKey` changes in addition to `state.sessionId` and `state.stage`. When `FILES_CHANGED` is dispatched it increments `fileRefreshKey`, which tears down and re-creates the polling effect — cancelling any in-flight `refreshFiles` call and restarting the 10-second timer from zero. This means file polling can be indefinitely deferred if `FILES_CHANGED` is dispatched frequently (e.g. during a long tool-call sequence). | severity: low | frontend/src/components/Chat.tsx:524-545

- [OBSERVATION] `startSession` is wrapped in `useCallback` with dep `[refreshFiles]`, and is listed as a dep of the `useEffect` at line 490-491. `refreshFiles` is itself a `useCallback` with no deps (`[]`). In practice these are stable, but `startSession` also calls `setSessionError`, `setUploadError`, `setStatusMessage`, `setSessionState`, `setServerFiles`, `setPendingFiles`, `setHasFetchedFiles`, `setUploadedFileNames` — all React state setters, which are stable by guarantee. No issue in practice, but the `useEffect` dependency on `startSession` means any future addition of a non-stable dep to `startSession` would cause the session-init effect to re-fire on every render, creating an infinite session-creation loop. | severity: low | frontend/src/components/Chat.tsx:489-491

- [OBSERVATION] `startSession` is an `async` function called inside a `useEffect` (line 490) without being wrapped or its returned promise tracked. Unhandled rejections from `startSession` propagating past its own `try/catch` (e.g. from `clearSessionId()` or synchronous throws in state setters) would result in unhandled promise rejections with no error boundary coverage. The effect does not return a cleanup function to cancel the in-flight session creation if the component unmounts before it completes. | severity: medium | frontend/src/components/Chat.tsx:489-491

- [OBSERVATION] In `startSession`, when a stored session ID exists and `getSession` succeeds (lines 455-461), `dispatch({ type: "RESTORE_SESSION", ... })` is called and the function returns. The `SET_INITIALIZING: false` dispatch in the `finally` block is only reached in the new-session path (lines 484-486). The `RESTORE_SESSION` reducer sets `isInitializing: false` directly (line 307), so this works, but if `getSession` throws (caught at line 464) and falls through to the new-session path, `dispatch({ type: "SET_INITIALIZING", value: true })` was already dispatched at line 450, and `SET_INITIALIZING: false` is correctly dispatched in `finally`. However, if `getSession` resolves but `meta` is truthy yet `refreshFiles` at line 461 throws synchronously (not possible since it's async, but if it rejects after `return`), the `isInitializing` state is already `false` from `RESTORE_SESSION` — so this is safe. The flow is correct but the dual-path `isInitializing` reset (via reducer vs. via explicit dispatch) is fragile. | severity: low | frontend/src/components/Chat.tsx:445-487

- [OBSERVATION] `handleNewChat` calls `await startSession()` (line 616) without a surrounding `try/catch`. If `startSession` throws (past its internal catch), the unhandled rejection propagates into `handleNewChat`'s returned promise, which is invoked via `onClick` handler at line 618 — React does not catch async errors thrown from event handlers in error boundaries, so the exception would become an unhandled promise rejection. | severity: medium | frontend/src/components/Chat.tsx:616

- [OBSERVATION] The `storeMessages` effect (lines 497-501) fires whenever `state.isStreaming` becomes `false` OR `state.messages` changes. During streaming, each `DELTA` action produces a new `state.messages` array reference. If `state.isStreaming` is `false` and a non-streaming action updates `state.messages` (e.g. `FILES_CHANGED` does not touch messages, but `ERROR` or `APPEND_ASSISTANT` does), `storeMessages` is called synchronously on every such update. This is low-overhead but writes the full messages array to `sessionStorage` on every action that changes messages while not streaming, including during `RESTORE_SESSION`. | severity: low | frontend/src/components/Chat.tsx:497-501

- [OBSERVATION] `getStoredMessages` in `session.ts` deserialises from `sessionStorage` with a cast `JSON.parse(raw) as ChatMessage[]` (line 26). There is no runtime validation of the parsed shape. A corrupted or outdated `sessionStorage` entry (e.g. from a previous app version with a different `ChatMessage` schema) will be returned as-is and passed directly to `RESTORE_SESSION`, potentially causing reducer or render crashes downstream. | severity: medium | frontend/src/lib/session.ts:25-28

- [OBSERVATION] `getFileContent` in `api.ts` appends `filename` directly as a URL query parameter via `URLSearchParams` (line 64). `URLSearchParams` percent-encodes the value, so path traversal sequences like `../../etc/passwd` become `..%2F..%2Fetc%2Fpasswd`. Whether the backend decodes and resolves these depends on the server implementation. The client performs no sanitisation or validation of `filename` before constructing the URL. | severity: medium | frontend/src/lib/api.ts:63-65

- [OBSERVATION] In `api.ts`, all fetch calls (`getSession`, `createSession`, `uploadFile`, `listFiles`, `getFileContent`) have no timeout or `AbortSignal` parameter (except `uploadFile` via the `withTimeout` wrapper applied in the caller). `listFiles` and `getSession` in particular are called from `refreshFiles` and `startSession` with no timeout, meaning a hung server will cause these to pend indefinitely, holding the UI in a loading state with no recovery path. | severity: medium | frontend/src/lib/api.ts:11-70

- [OBSERVATION] `uploadFile` reads the error body with `res.text()` (line 39) and interpolates it directly into the thrown `Error` message: `Upload failed (${res.status}): ${detail}`. This string is then passed through `friendlyError` which returns the fallback for unrecognised messages. The raw server response is not rendered in the UI directly (it goes through `friendlyError`), so XSS is not a risk here, but server-controlled content appears in the Error message object and could leak sensitive server internals in logged errors. | severity: low | frontend/src/lib/api.ts:38-42

- [OBSERVATION] In `ArtifactCanvas.tsx`, `handleDownload` (lines 73-80) constructs a download using `filename` directly as the `a.download` attribute value. If `filename` contains path separators (e.g. `../../evil.sh`), browsers sanitise the download name, but the `a.click()` is called on a detached element without appending it to the DOM first. This works in Chrome/Edge but is not reliable across all browsers (Firefox requires the element to be in the document). Additionally `URL.revokeObjectURL` is called synchronously after `click()`, which can cause the download to fail before the browser has fetched the blob URL. | severity: low | frontend/src/components/ArtifactCanvas.tsx:73-80

- [OBSERVATION] In `ArtifactCanvas.tsx`, the `CsvTable` component splits on `","` (line 27) without handling quoted fields containing commas (RFC 4180). A CSV cell value like `"Smith, John"` will be split into `["\"Smith"`, `" John\""]`, then the `replace(/^"|"$/g, "")` strips only leading/trailing quotes on each fragment, producing corrupted cell values. This is a data integrity issue for any CSV with quoted fields. | severity: medium | frontend/src/components/ArtifactCanvas.tsx:27

- [OBSERVATION] In the `ASSISTANT_START` reducer case (lines 152-191), the condition at line 175 checks `last.role === "assistant" && last.isStreaming && state.currentRunId` to detect a post-tool-call text continuation and returns `state` unchanged (same message). However, `state.currentRunId` is set by `RUN_STARTED` which arrives before any text events. If `RUN_STARTED` is received, then `TOOL_CALL_START`/`TOOL_CALL_END`, then a second `TEXT_MESSAGE_START` arrives — but `state.currentRunId` is still set (it is only cleared by `DONE`). The condition will match and the new text will be appended into the same message part, which is the intended behaviour. But if two separate `RUN_STARTED` events arrive without an intervening `DONE` (malformed server output), `currentRunId` is overwritten and the first run's continuation detection breaks silently. | severity: low | frontend/src/components/Chat.tsx:175-177

- [OBSERVATION] The `TOOL_ARGS` reducer (lines 230-243) and `TOOL_END` reducer (lines 245-258) both call `updateLastMessage`, which always operates on the last message in the array. If `TOOL_CALL_ARGS` or `TOOL_CALL_END` events arrive for a tool call that is not in the last message (e.g. a delayed event from a previous run, or a server sending events out of order), the reducers will attempt to find `toolCallId` in the wrong message's parts, find no match, and silently return the parts unchanged — the tool call's args and completion status will be lost. | severity: medium | frontend/src/components/Chat.tsx:230-258

- [OBSERVATION] In `handleStop` (lines 619-625), after aborting the stream and dispatching `DONE`, an `APPEND_ASSISTANT` is dispatched with the stop message (line 624). `DONE` sets `isStreaming: false` and closes the last message. `APPEND_ASSISTANT` then adds a new message. However, the `for await` loop in `handleSend` may still be in the process of yielding events (between `abort()` being called and `AbortError` being thrown at the next `await`), and those events will be dispatched to `handleAGUIEvent` after `DONE` has already been processed, potentially appending text or tool events to what should be a completed message. | severity: medium | frontend/src/components/Chat.tsx:619-625

- [OBSERVATION] `useEffect` at lines 497-501 stores messages to `sessionStorage` when `!state.isStreaming && state.messages.length > 0`. During the `RESET_FOR_NEW_CHAT` action, `messages` is reset to `[]` and `isStreaming` to `false`. The effect then fires with `state.messages.length === 0`, so the condition `state.messages.length > 0` prevents overwriting storage with an empty array — correct. But `clearSessionId` (which also removes `MESSAGES_KEY`) is called in `handleNewChat` before `dispatch(RESET_FOR_NEW_CHAT)` (line 596 vs. 614), so the storage is cleared before the effect fires. If `startSession` then calls `storeSessionId` before the effect runs, there is a brief window where a new session ID is stored but the message key is absent — consistent, not a bug, but the ordering is load-bearing. | severity: low | frontend/src/components/Chat.tsx:596-614

- [OBSERVATION] The `handleIntakeUpload` callback (lines 547-583) transitions to `"chat"` stage via `dispatch({ type: "SET_STAGE", stage: "chat" })` at line 573 only on successful upload. If the user uploads a second file on the intake screen before the first upload completes (the `isUploading` state is set but the intake screen may not fully disable the upload control), a second call to `handleIntakeUpload` would run concurrently, both racing on `setIsUploading`, `setUploadState`, `addPendingFile`, and `refreshFiles`. There is no mutex or in-flight guard beyond the `isUploading` React state, which is not atomically checked-and-set. | severity: low | frontend/src/components/Chat.tsx:547-583

- [OBSERVATION] `RESTORE_SESSION` is dispatched (line 459) with messages returned by `getStoredMessages()`, which filters out `isStreaming: true` messages (in `storeMessages` at `session.ts:34`). However, restored messages may have `toolActivity` entries with `status: "running"` (if a tool call was in progress when the page was last closed), because `storeMessages` only excludes the whole message if `isStreaming`, not individual tool parts. These stale `"running"` tool indicators will appear in the UI as perpetually-spinning tool calls after session restore. | severity: medium | frontend/src/components/Chat.tsx:459 and frontend/src/lib/session.ts:34
